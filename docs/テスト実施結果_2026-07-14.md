## テストであぶり出した不具合（要対応）

### 【高】A. マイページが「ログイン本人」でなく baba 固定（IT-MYP-01・確定）
- 内容：`App\Support\PersonalCases::meModel()` がログイン中のユーザーを見ず、固定で E-007（baba）を返す。誰でログインしても baba のデータがマイページに出る（個人情報の観点で要修正）。
- 実証：別の社員（E-200）でログインして本人判定させると、期待 `E-200` に対し実際 `E-007` が返り失敗することを確認済み。
- 直し方（案）：`meModel()` を `Auth::user()`（社員判定つき）を返すよう変更。修正後 `MyPageOwnDataTest` の `markTestSkipped` を外せば緑になる。

### 【高】B. アサインを同じ案件×同じ日に保存し直すと 500（開発SQLiteで発生）
- 内容：`AssignmentController::save()` の上書き削除が `where('date', $date)`（$date＝日付のみ）だが、`date` カラムは時刻付き（`2026-09-01 00:00:00`）で保存されるため一致せず、削除が空振り→再登録で unique 制約に衝突して 500。
- 影響：本番 MySQL（date型は日付のみ保持）では出ない見込みだが、**現状の開発環境（SQLite）では発生し得る**。同一ファイル内の `quickToggle()` は既に `whereDate('date', $date)`（「D決めの500対策」）を使っており、`save()` だけ取り残されている。
- 直し方（案）：`save()` の削除条件を `whereDate('date', $date)` に統一する。

### 【中】C. マスタ採番SQLが本番MySQLで構文エラー（SQLiteでは検出不可・要MySQL確認）
- 内容：`MasterController::nextContentId()` の `orderByRaw('CAST(SUBSTR(id, 4) AS INTEGER) DESC')` は SQLite では通るが、**MySQL では `AS INTEGER` が構文エラー**（正しくは `AS SIGNED`）。コンテンツ登録が本番で落ちる。
- 状況：開発SQLiteのテストでは「採番が連番になる」ことは確認済み（合格）。だが MySQL 非互換はSQLiteでは原理的に検出できないため、**MySQL実行（ST-DB-01）での確認が別途必要**。
- 直し方（案）：生SQLをやめ、`ProjectController::resolveContentIds` が既にPHP側で行っている採番に寄せる（重複コードの解消にもなる）。

## 補足・設計上のポイント

- ログイン後の業務画面は「メール2段階認証(OTP)」でガードされている（`EnsureTwoFactor`）。そのため認証以外のテストでも「OTP確認済み」を作る必要があり、`actingAsPerson()` に集約した。移行でOTPの条件が変わっても、直すのはこの1か所だけで済む。
- factory はモデルに `HasFactory` を付けず、テストから `PersonFactory::new()` 形で呼ぶ運用（既存モデルに手を入れない方針）。将来 `HasFactory` を付けて `Person::factory()` 形に統一するのも可（要判断）。

# ECS テスト計画書

- 版：v0.1（初版）
- 作成日：2026-07-14
- 対象システム：ECS（イベント運営スタッフ アサイン管理システム / Laravel 13・PHP 8.3）
- 位置づけ：本番リリース前に「各機能が仕様どおり動くこと」を確認するためのテスト全体計画。詳細な確認項目は別紙「テスト仕様書」に記載する。

---

## 1. 目的

- リリース前に、単体・結合・システムの3レベルで機能を検証し、重大な欠陥を残さずに公開できる状態にする。
- 変更のたびに壊れていないか自動で確認できる土台（自動テスト）を用意し、以降の開発の安全網とする。
- 4つの立場（エンジニア／営業／イベプラ／イベントスタッフ）で洗い出した既知の懸念（別紙「ECS改善点_4立場ヒアリング」）を、テスト項目として取り込む。

## 2. テスト対象の範囲

### 対象（In Scope）
- 認証・権限（4段階：スタッフ／社員／管理者／Administrator）※実装は Breeze/Fortify 移行後
- 案件管理（登録・一覧・編集・下書き・CSV一括取込・詳細保存）
- アサイン（D決め・手動アサイン・公開ボード・アサイン表・希望まとめ・エントリー）
- マスタ管理（コンテンツ・拠点・ポジション別必要人数）
- 名簿（スタッフ・社員・CSV一括取込・経験コンテンツ）
- スタッフ本人機能（スタッフポータル・プロフィール・パスワード変更・初回設定）
- 個人機能（マイページ・収支入力）
- 運用支援（人数確定リマインド／チャットワーク連携・謎解き紙在庫・設定/MTG日）

### 対象外（Out of Scope・今回）
- 本番インフラ（AWS・RDS）そのものの性能/可用性試験 … デプロイ後に別途
- 負荷試験・セキュリティ診断（ペネトレーションテスト）… 別計画
- モックのみで未実装の画面挙動（`/assign-detail` 等）… 「保存されない仕様」であることの確認にとどめる

## 3. テストレベルの定義

| レベル | 狙い | 主な手法・ツール | 実施形態 |
|---|---|---|---|
| 単体テスト（Unit） | 個々の部品（モデル・Support クラス・計算ロジック）が単独で正しく動くか | PHPUnit（`tests/Unit`）。DBに依存しない純粋な計算は特に自動化 | 自動 |
| 結合テスト（Integration / Feature） | 画面〜コントローラ〜DBが一連でつながって動くか（HTTPリクエスト単位） | Laravel Feature テスト（`tests/Feature`）。テスト用DB（SQLite :memory:）にデータを入れて検証 | 自動 |
| システムテスト（System / E2E） | 実際の利用シナリオを人・立場ごとに通しで確認 | 手動チェックリスト（ブラウザ操作）。必要に応じて Laravel Dusk（ブラウザ自動化）を追加検討 | 手動（一部自動化候補） |

> 補足：Laravel では「結合テスト」を Feature テストと呼ぶ。1リクエストでルート→ミドルウェア→コントローラ→DBまで通すため、実務上いちばん費用対効果が高い。本計画の主力はここに置く。

## 4. テスト環境

| 項目 | 内容 |
|---|---|
| 自動テスト用DB | SQLite（メモリ上 `:memory:`）。`phpunit.xml` で設定済み。テストごとにまっさらな状態で実行され、本番/開発データを汚さない。 |
| 開発DB | SQLite（`database/database.sqlite`）。現在ローカルで稼働中。 |
| 本番相当DB | MySQL 8.x（ローカル導入済み・AWS RDS はデプロイ後）。**MySQL固有の非互換（後述リスク）を結合テストで別途確認する。** |
| メール/キュー | テスト時はダミー（`MAIL_MAILER=array`, `QUEUE_CONNECTION=sync`）。 |
| チャットワーク送信 | テストでは実送信しない（ドライラン／モック）。 |

## 5. 使用ツール

- PHPUnit 12（導入済み）／`php artisan test`
- FakerPHP（テストデータ生成・導入済み）
- モデルファクトリ（`database/factories/`）＋テスト用シーダ（新規作成予定）
- Laravel Pint（コード整形・導入済み）
- （検討）Laravel Dusk … ブラウザE2E自動化が必要になった場合に追加

## 6. テストデータ方針

- 各主要モデル（Person／Project／Content／Assignment／ContentRoleRequirement／ShiftPreference／Application 等）に **ファクトリ** を用意し、テストごとに必要な最小データを都度生成する。
- 権限テスト用に「スタッフ・社員・管理者・Administrator」各1名を作るヘルパを用意する。
- 実データ（本番/開発）はテストに使わない。自動テストは毎回まっさらなメモリDBで完結させる。

## 7. 合格基準（Entry / Exit Criteria）

### 開始条件（Entry）
- テスト仕様書がレビュー済み。
- テスト用ファクトリ／シーダが用意され、`php artisan test` が空実行で通る。

### 終了条件（Exit）
- 仕様書の全テストケースを実施し、結果（合否）が記録されている。
- 重大度「高」の不具合が 0 件（回避策なしのブロッカーが無い）。
- 自動テスト（単体＋結合）がすべてグリーン。
- 既知の残課題（中・低）は一覧化し、リリース可否をエンジニア／責任者が判断できる状態。

### カバレッジ目標（目安）
- 権限ゲート・アサイン保存・案件登録・CSV取込・プロフィール保存など「壊れると痛い経路」は結合テストで必ず1本以上。
- 数値目標（行カバレッジ%）は初版では必須とせず、重要経路の網羅を優先。

## 8. 進め方・スケジュール（段階）

小さく分けて、動かしながら進める。

1. **フェーズ0：準備**（今）… テスト計画書・テスト仕様書の作成／ファクトリ・シーダ整備。
2. **フェーズ1：単体テスト** … 認証に依存しない計算・判定ロジック（開催日までの日数、稼働率、締切ルール、役割コード、紙在庫集計 など）。
3. **フェーズ2：結合テスト（認証以外）** … 案件・アサイン・マスタ・名簿・収支・リマインド・紙在庫・設定。ログインが要る画面は、テスト用ログインヘルパで代替。
4. **フェーズ3：認証・権限テスト** … **Breeze/Fortify 移行完了後に着手**。ログイン・2段階認証・パスワードリセット・4段階の権限ゲート。
5. **フェーズ4：システムテスト（手動）** … 4立場の利用シナリオを通しで確認。MySQLでの結合確認もここで実施。
6. **フェーズ5：リリース判定** … 結果集計・残課題の棚卸し・可否判断。

> 認証まわり（フェーズ3）は Breeze/Fortify への移行中のため、移行が落ち着いてから着手する（作り替え中に書くと手直しが二度手間になるため）。

## 10. リスク・前提（既知の注意点）

別紙「4立場ヒアリング」で判明した、テストで特に狙うべき点：

- **認証が移行中**：Breeze/Fortify 化の最中。認証テストは移行完了後（フェーズ3）。
- **本番MySQLで壊れる箇所がある**：`MasterController` のID採番に SQLite 専用SQL（`CAST(... AS INTEGER)`）があり、MySQLで構文エラーになる。→ 結合テストを MySQL でも回して検出する。
- **一部データがコード直書き（7月固定）**：希望まとめ・ダッシュボード・D決めの対象月がハードコード。→ 月替わりを想定したテストで検出する。
- **「保存されない」画面がある**：収支・エントリー・稼働希望などが localStorage 止まり。→ 「保存後に再取得すると残っているか」を結合テストで検証（未実装なら不具合として記録）。
- **権限ゲートの抜け**：他人の出勤可能日の上書き、案件作成/削除の権限ズレ。→ 権限テスト（フェーズ3）で網羅。
- **本物/見本の混在**：モック画面（`/assign-detail` 等）は「保存されない仕様」として扱い、業務動線の主役（`/project-assign`）を正としてテストする。

## 11. 不具合管理

- 発見した不具合は「ID・画面・重大度（高/中/低）・再現手順・期待/実際・状態」で一覧管理する（別紙の結果欄、または課題表）。
- 重大度「高」は原則リリース前に修正。中・低は棚卸しして判断。
